# Aurora 首页与游戏页合并计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. 按复选框记录进度。本文和 HTML 演示先供用户评审；正式界面实施以用户确认后的版本为准。

**Goal:** 将首页和游戏页合并为默认打开的“游戏库”，让用户在一个页面完成添加游戏、确认发布包、查找游戏和进入安装／修复／还原流程。

**Architecture:** 保留现有 Electron IPC、游戏数据和详情面板；用一个纯展示模型统一 Aurora 状态、筛选、计数和排序。主列表只渲染一份游戏数据，历史页承接操作历史和当前会话日志。

**Tech Stack:** 现有 CommonJS、原生 HTML/CSS/JavaScript、Electron、Node 内置测试。不新增 UI 框架或运行时依赖。

**Spec:** 原设计 `docs/superpowers/specs/2026-09-26-aurora-swapper-design.md`；本计划“交互约定”是待评审的增量设计。HTML 演示位于 `docs/prototypes/aurora-game-library.html`。

## 交互约定

### 1. 页面结构

1. 左侧五个导航：游戏库、插件、历史、设置、关于；默认进入游戏库。
2. 标题行：游戏库、库内游戏总数；右侧“重新扫描”和“添加游戏”。
3. 发布包状态条：紧凑展示状态和“更换”入口。未配置显示“选择发布包”；路径放在设置或展开详情中。
4. 搜索、排序和“更多筛选”。
5. 状态筛选：全部、已安装、未安装、安装未完成。每个游戏只计数一次。
6. 游戏列表。沿用现有卡片和按来源分组设置；不再额外渲染最近游戏卡片。
7. 大面积添加引导仅在库为空时出现；已有游戏时可继续拖入游戏文件夹。

### 2. Aurora 状态来源

- 状态只来自 `window.lab.auroraState()` 中的 `records`。该 IPC 已将未完成事务映射为 incomplete，展示层沿用这个结果。
- 不再用 `gameFilters.isInstalled()` 的旧 Swapper/DLSS/插件扫描结果代表 Aurora 已安装。
- 游戏目录和安装目录可以不同；保留当前 `auroraCoversGame` 的目录边界规则，例如 `Game/bin` 属于 `Game`，`Game2` 不属于 `Game`。
- 同一游戏匹配多个记录时：存在 incomplete 则显示安装未完成，否则存在 installed 则显示已安装；没有记录才显示未安装。
- 记录读取失败、未知记录状态或路径记录冲突时展示“状态待确认”；不能把这些情况计作未安装。服务侧仍负责最终冲突拦截。
- store 损坏时显示全局警告和真实记录文件路径，禁用修改按钮，仍允许浏览库和历史。不显示虚假的已安装／未安装统计。
- “安装未完成”表示已有未解决记录，不把它描述成检测到游戏损坏。详情提示用户先处理恢复。

### 3. 搜索、排序与筛选

- 搜索支持名称和目录，不区分文本大小写；与 Aurora 状态及更多筛选按 AND 组合。
- 默认按最近操作排序，其他选项为名称 A–Z、名称 Z–A。
- 最近操作使用历史返回的 `rows[].dir/date/action`，匹配 install、repair、restore、recovery；不把打开详情伪装成操作成功。
- 无有效操作时间的游戏排在有时间之后；同一时间按名称排序。历史不可用时降级按名称排序，游戏库仍可正常使用。
- 按来源分组开启时，维持现有来源顺序，并在组内排序；关闭后按全库排序。文案避免承诺分组时是全库时间顺序。
- 状态标签上的计数以完整游戏库为基准；搜索后另显示“当前显示 X / 总计 Y”。
- 更多筛选保留 API、DLSS 存在状态和插件存在状态；首次收起。删除把旧 Swapper “已安装”混入 Aurora 状态的选项。
- 没有匹配结果时显示“清除筛选”；库为空时显示“添加游戏”。这两个空状态必须区分。

### 4. 添加和发布包

- “添加游戏”展开两个明确入口：“添加单个游戏”和“添加游戏库文件夹”，分别复用当前 addGame/addFolder 的处理流程。
- 拖入行为复用 Electron 的 pathForFile 和现有目录检查；遇到非目录给出提示，避免默默忽略。
- 添加重复目录不重复插入卡片；添加后保留当前库数据。如果筛选隐藏了新游戏，给出“已添加，查看此游戏”入口。
- 发布包未指定时仍可浏览游戏；禁用安装／修复，但已有安装记录仍可以还原。
- 发布包状态条和设置页共用选择逻辑。选择取消不改变原配置；无效包显示原有校验原因。
- 记录损坏时禁用包选择和所有游戏修改操作，与当前规则一致。

### 5. 游戏详情与反馈

- 卡片点击进入原有详情面板，键盘 Enter 同样可用，右键菜单保留。
- 普通未安装：展示“安装 Aurora”；已安装：展示重装、修复运行库、还原；有未解决事务：突出还原入口。
- 操作执行期间继续使用现有 jobRunning 和主进程游戏锁。按钮状态、未确认游戏关闭的提示和失败输出必须保留。
- 操作结束后统一刷新 Aurora 状态、当前卡片、筛选计数和最近操作排序；失败按实际存储状态渲染。
- 新查询应覆盖旧查询；延迟返回的数据不得覆盖较新的安装／还原结果。

### 6. 日志与历史

- 游戏详情保留当前操作输出和复制／保存诊断入口。
- 历史页增加“操作历史 / 本次运行日志”切换，分别沿用现有 history 和 state.log 数据。
- 当前会话日志不承诺跨重启保存，清空日志只清当前会话显示；不要误删持久历史。
- 移动现有 log、copyLog、clearLog 节点并同步事件绑定，避免旧首页 DOM 移除后启动报错。

## 本轮 HTML 演示的检查方式

- 初始“日常使用”：六张示例游戏卡片，状态 3 已安装 / 2 未安装 / 1 安装未完成。
- 切换四个状态、输入搜索、选择排序、展开更多筛选，观察列表和显示数量。
- 点击安装未完成的游戏，模拟还原后查看状态计数与历史更新。
- 选择“首次打开”：观察空库引导；选择发布包、模拟添加游戏，再从详情模拟安装。
- 选择“未配置发布包”：已有记录可以模拟还原，安装／修复按钮不可用。
- 选择“记录异常”：状态标签改为待确认，所有修改操作禁用，但仍可浏览。
- 演示不读取实际游戏目录，刷新页面会重置示例数据。
